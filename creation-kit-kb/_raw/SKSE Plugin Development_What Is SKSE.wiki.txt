If you are new to this, the single most useful thing to learn first is that the word "SKSE" can mean at least four different things, and almost every point of confusion comes from them being used interchangeably. This page attempts to separate them, and shows how they fit together.

When you read "SKSE" or "Requires SKSE", the author could mean any one of these.

== The hourglass ==

SKSE has a runtime half (present in the running game) and a build-time half (what a developer compiles against). The two halves meet at one seam: the '''plugin ABI'''

== Which SDK should a developer use? ==


<blockquote>
'''Please note that this information is in flux. Forks are abandoned or shift owners. The information here could be outdated by the time you read it. Please verify that the project you build against is actively maintained.'''
</blockquote>


There are two ways to build an SKSE plugin, and for most developers CommonLibSSE, not SKSE's own source.

* '''SKSE's own source''': The runtime, but also usable directly as an SDK. Building against it is lower-level and tends to be less ergonomic for any user not already familiar with reverse engineering techniques.
* '''CommonLibSSE''': A separately-authored library that most plugin developers build against for its easier C++ API. It looks and behaves more like how a developer might interact with a game. It targets the same plugin ABI at the waist, so a CommonLibSSE plugin loads under the same SKSE runtime. At compile time, commonlibsse it is a separate codebase: it re-derives the game's types itself and even redeclares the plugin-ABI structs, so its headers and SKSE's own cannot be included alongside each other. You build against only one.

CommonlibSSE ''''NG'''' also provides functionality which allows it to handle different versions/patches of Skyrim. Since some users opt to downgrade for compatibility reasons, it may be advisable to use this fork to maximize compatibility of your own mod.
